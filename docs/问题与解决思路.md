# Choreoglyph：问题与解决思路

本文选取 Demo 开发过程中真实遇到或在测试中发现的工程问题。每项分别说明问题、难点、处理方案和当前状态；“建议”不等于“已经修复”。少量 Swift 代码是项目实现的局部摘录，省略了无关上下文；不包含完整源码、关卡答案、内部日志和原始美术资源。

## 1. 场景类职责过重

**问题：** 游戏场景同时负责棋盘绘制、鼠标/触摸/键盘输入、冲突判断、候选笔记、撤销、动画、音效和页面跳转。增加功能时，一个场景类容易变成难以修改的“大对象”。

**难点：** 规则计算和 SpriteKit 节点更新交织在一起，测试一条玩法规则也可能需要启动图形界面；macOS 与 iOS 的输入代码还容易重复实现同一规则。

**解决：** 将棋盘规则抽为不依赖 SpriteKit 的纯 Swift `PuzzleEngine`。场景把用户输入转换为引擎操作；引擎返回操作结果和完成事件；场景决定相应的颜色、音效和表演。两个平台共享规则层，分别适配输入层。

项目代码摘录：引擎返回事实和事件，而不是直接操作舞台节点。

```swift
enum PuzzleEvent: Equatable, Sendable {
    case rowCompleted(Int), columnCompleted(Int), regionCompleted(Int), puzzleCompleted
}

struct MoveResult: Sendable {
    let index: Int
    let value: Int
    let isNote: Bool
    let conflicts: [Int]
    let isCorrect: Bool
    let events: [PuzzleEvent]
}
```

**状态：** 规则与表现的第一层解耦已完成，核心规则可单独测试。输入、动画、渲染和会话职责仍可继续拆分。

## 2. 完成状态与棋盘实际状态不同步

**问题：** 已完成的行、列或区域被玩家改错后，完成标记可能仍然保留；再次修正时，完成反馈不再触发。全盘正确性判断和局部演出因此可能不同步。

**难点：** “完成”既是当前棋盘的判断结果，也是事件发生的边沿状态。只有“未完成→完成”应产生新事件；“完成→未完成”要清除标记；保持完成不能重复奖励。普通覆盖、擦除和候选模式还必须一致。

**解决思路：** 每次编辑只重算受影响的行、列和区域，比较编辑前后的状态，再更新完成集合及事件。增加“完成→改错→修正”的回归测试，验证状态与反馈重新同步。

**状态：** 领域测试已复现该问题，修复方案明确，但尚未标记为已修复。

## 3. 撤销不只是恢复一个格子

**问题：** 一次输入可能同时改变格子值、候选标记和完成集合。如果撤销只回退格子值，界面看起来恢复了，内部规则状态却可能不一致。

**难点：** 逐项反向操作需要覆盖填写、候选切换、擦除及关联候选移除等不同路径，遗漏一处就会产生隐蔽错误。

**解决：** 修改前保存完整的 `PuzzleSnapshot`，其中包含棋盘值、候选笔记及行/列/区域完成状态；撤销时整体恢复，并给历史记录设置上限。

项目代码摘录：撤销恢复的是一份完整状态，而非单个格子的旧值。

```swift
func undo() throws {
    guard let previous = history.popLast() else { throw PuzzleError.emptyHistory }
    values = previous.values; notes = previous.notes
    completedRows = previous.completedRows; completedColumns = previous.completedColumns
    completedRegions = previous.completedRegions
}
```

**取舍与状态：** 小棋盘下快照复制成本可接受，换来实现简单和状态一致性。撤销与重置已纳入规则测试；若未来棋盘规模显著扩大，再考虑增量差异记录。

## 4. 随机关卡既要变化，也要稳定可复现

**问题：** 不受控的随机生成会使同一关再次打开时内容变化，玩家反馈的问题难以重现；随机生成的谜题也可能重复或有多个解。

**难点：** 生成一份完整答案不等于生成有效谜题，还要检查行、列、区域、提示格、唯一解与不同关卡间的重复。

**解决：** 使用确定性随机种子生成候选内容，进行约束与重复检查，再通过回溯求解器统计解数；发现多个解时可以提前停止并重新生成。

**验证与状态：** 系统测试对当前 40 个关卡执行了规则、唯一解和重复检查，并逐关验证通关事件。这是对当前测试集的结论，不代表未来新增内容无需验证。

## 5. 多窗口下本地存档可能丢失更新

**问题：** 两个窗口各自持有进度对象时，较旧的内存状态可能在稍后保存，覆盖另一个窗口刚写入的关卡进度或奖励余额。

**难点：** `UserDefaults` 能持久化，却不会自动合并多个 Store 的快照。关卡集合可以取并集，奖励余额却不能简单取最大值，因为兑换同时涉及扣减和幂等。

**解决思路：** 优先在应用层共享唯一进度 Store。若需要真正的多窗口独立写入，则增加版本检查、重读合并或事件化更新；若产品不支持多窗口，平台配置也应与此一致。

**状态：** 存储层测试已复现旧状态覆盖；真实设备上的双窗口交互尚未完整验证，方案待实施。

## 6. 快速点击造成按钮位置漂移

**问题：** 部分普通按钮在连续快速按下/释放后，可能逐次偏离原始位置；仅使用缩放反馈的主按钮不受同一种位移机制影响。

**难点：** 第二次点击可能发生在第一次动画结束前。旧动作被移除时，节点并不会自动回到静止位置，下一次相对位移从错误坐标继续累加。取消点击也存在同类路径。

**解决思路：** 保存按钮的基准位置，按下、释放和取消都以基准位置计算绝对目标；开始新动画前归位。回归测试覆盖连续点击、移出按钮松开和不同帧率。

**状态：** 原生渲染测试已复现位移累积；尚未标记为修复完成。

## 7. 角色动作中断后的姿态恢复

**问题：** 若角色正在执行相对移动或旋转，新的动作提前开始，角色可能从中途姿态继续运动。

**难点：** `SKAction` 被移除并不会自动还原节点坐标和旋转。直接在角色根节点反复叠加动作，会把舞台上的基准位置与临时演出位移混在一起。

**解决思路：** 用根节点保存角色基准姿态，子节点承载临时动作；切换时只清理并重置子节点，再播放新动作。同时覆盖重复触发和离开场景的清理路径。

**状态：** 目前是静态检查发现的风险，未在完整关卡交互中测得实际漂移，不将其写成已复现缺陷。

## 8. 跨平台导航与场景生命周期

**问题：** macOS 与 iOS 的应用入口、窗口容器和输入事件不同，主页、关卡选择、游戏及记录页面却需要相同的导航语义。场景若直接操作平台窗口，会增加重复与耦合。

**难点：** 场景切换不只是一张画面的替换，还涉及旧节点、监听、音频和未保存对局；SwiftUI 承载 SpriteKit 场景时也要避免复用旧实例。

**当前处理：** 场景通过回调表达导航意图，平台入口分别协调实际切换。玩法规则保持平台无关，输入和生命周期差异留在适配层。

项目代码摘录：GameplayKit 状态机明确列出流程状态，场景导航则由外部回调处理。

```swift
private let flow = GKStateMachine(states: [
    PlayingState(), AnimatingState(), PausedState(),
    CelebratingState(), RewardState(), ResultState()
])
```

**状态：** 基础双平台路由已建立。菜单离开未保存对局的确认或临时存档，以及统一的跨平台协调器，仍是后续工作。

## 9. Bundle 资源路径与配置校验

**问题：** 图片、音频和 JSON 在不同目标与构建方式下可能位于不同 Bundle 子目录。场景各自查找文件会重复代码，路径大小写或 Target Membership 错误还可能直到运行时才暴露。

**难点：** 编译通过不代表某个页面必需的资源已经进入包；配置中的资源引用也必须与实际打包结果保持一致。

**当前处理与方案：** 已对内容配置的尺寸、索引和关联数据做加载校验。下一步把图片、音频和 JSON 的路径查找收敛到统一的资源访问层，在启动或测试阶段检查必需资源，并提供明确错误提示。

项目代码摘录：加载后的关卡会先校验棋盘数组、值域和给定格索引。

```swift
let total = size * size
guard size > 0, solution.count == total, regions.count == total
else { throw ContentError.invalidBoardSize }
guard solution.allSatisfy({ (1...size).contains($0) })
else { throw ContentError.invalidSolution }
guard givens.allSatisfy({ solution.indices.contains($0) })
else { throw ContentError.invalidGiven }
```

**状态：** 配置校验已采用；跨场景统一资源访问和生产环境的错误恢复尚待完成。

## 10. 编译通过不等于发布就绪

**问题：** 规则测试和 macOS/iOS 构建通过，仍不能证明真机触控、后台恢复、音频中断、长时间性能和商店上传没有问题。

**难点：** 纯逻辑测试、模拟器、真机、Release 编译与正式发布覆盖不同风险。把它们统称“测试通过”，会夸大当前结论。

**当前处理：** 按测试层级记录结果与未覆盖范围：规则和关卡、界面冒烟、平台编译，以及待执行的设备和发布验证。无签名 Release 编译只证明目标可编译，不等于真机安装或上架成功。

**状态：** 当前规则与主要流程具备测试证据，完整发布验证仍待进行。具体见[测试与说明](测试与说明.md)。

## 总结

这些案例说明：实现正确路径只是第一步，更重要的是明确状态归属、事件边界、生命周期、并发写入和异常路径。已采用的处理与待修复的方案在文中分别标注，避免把设计思路误写成已交付结果。
